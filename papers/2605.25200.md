## Summary

This paper introduces GroupTravelBench, the first benchmark specifically designed to evaluate large language model (LLM) agents in complex, multi-user travel planning scenarios. Unlike previous benchmarks focused on single users, GroupTravelBench addresses the challenge of managing group dynamics, requiring agents to identify user preferences, resolve conflicts, and plan fair itineraries across multiple turns. The researchers created 650 diverse tasks using real data, built an interactive evaluation environment, and found that even advanced LLMs struggle significantly with group coordination and achieving fair solutions.

## Technical note

GroupTravelBench is the first benchmark for multi-user, multi-turn travel planning, comprising 650 tasks over three difficulty levels built from real user profiles, POI data (~338K entries), and ticket prices, each run in a synchronous group-chat sandbox with 250K cached tool records for reproducible offline evaluation. Beyond single-user tool use, it probes three group-specific capabilities: eliciting private hierarchical preferences (must/prefer/avoid/reject), coordinating inter-user conflicts via compromise or subgrouping, and balancing group utility against fairness. Deterministic scoring is enabled by three coexisting preference tables per user—original ground truth, agent-inferred belief, and post-compromise effective—so elicitation and conflict resolution can be measured without exposing updates to the agent. It pairs rule-based outcome metrics with an LLM judge for process quality, and finds even frontier agents fail all four outcome metrics, with plan validity below 12%.

- On validation success: the marker is parsed, the modification is applied to $\mathbf{p}_{i}^{\text{eff}}$ via dotted-path traversal, the marker is stripped from the visible message, $\kappa_{i}$ is decremented, and if $\kappa_{i}$ reaches 0, the user’s system prompt is rebuilt to mark them as non-compromisable

- The tool call’s normalized argument JSON is used as the cache key
- If an exact match exists, the cached response is returned immediately
- If no exact match exists (cache miss), the system falls back to the embedding-retrieval + ICL simulation strategy (§[B.3](#A2.SS3))
- Each tool has a dedicated JSON cache file, avoiding cross-tool key collisions
- Cache writes are thread-safe and use atomic file operations (write to temp file, then rename) to prevent corruption under concurrent access
- An auto-save mechanism flushes dirty entries to disk every 30 seconds
- Cache misses during evaluation are logged to separate *_missed.json files for later batch refresh
- Embedding precomputation: We precompute embeddings for all cached tool-call inputs using Qwen3-Embedding-8B, deployed as a remote embedding service. Embeddings are stored as .npz files alongside each tool’s cache
- FAISS-based retrieval: When a cache miss occurs, the current tool call’s input is embedded and used to query a FAISS index (built at startup) to retrieve the top-8 most similar cached entries
- ICL simulation: The retrieved (input, output) pairs are formatted as few-shot examples, along with the tool’s schema definition. A tool-simulator LLM generates a plausible response that is consistent with the real tool’s output format and the retrieved examples
- Transparent logging: Simulated responses are saved to the missed-calls file but are *not* written back to the main cache, ensuring that the primary cache remains a faithful record of real API responses
