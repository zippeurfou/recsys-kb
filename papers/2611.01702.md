## Summary

SparseLift addresses the challenge of optimizing large-scale recommendation models, specifically their "sparse path" involving sparse operations and communication, which are currently represented as opaque nodes hindering effective whole-graph optimization. It does so by being a compiler that analyzes the model structure and runtime, then reconstructs these opaque nodes into analyzable subgraphs, thereby exposing the underlying resource semantics to the optimization system. This allows SparseLift to automatically plan and reuse optimized execution strategies, significantly boosting training throughput by 16.5% on industrial data and achieving 1.6x and 1.26x speedups on the DLRM benchmark compared to existing baselines.

## Technical note

Tencent video-platform recommendation training (1B dense and 100B sparse parameters, billions of samples per day, RankMixer backbone with multitask towers, sparse parameters on dedicated parameter servers, 8xH20 nodes). Problem: the sparse path (per-table embedding lookup, input and gradient reorganization, all-to-all collectives) shows up as opaque runtime calls in the training graph, so whole-graph compilers cannot fuse, overlap or reorder it, and existing fixes (TorchRec, PICASSO, FusedRec, EMBark) are rules tied to one runtime. Method: SparseLift is a low-overhead compiler that lifts the sparse path into an analyzable semantic graph plus a read-only Sparse Resource Semantic View (data deps, parameter versions, buffer lifetimes, collective ordering), scores four candidate transformations against the incumbent plan with incremental cost models (communication aggregation into pack-collective-unpack subgraphs, cross-table subgraph parallelism on streams, Triton code generation for structurally compatible per-table work, one-step-lookahead latency hiding), and a constraint-aware planner emits an execution plan reused across steady-state steps, integrated via sparselift.compile with one adapter per runtime. Results: +16.5% median steady-state throughput on the industrial task at 8 GPUs (4334.6 -> 5050.7 samples/s), step time 451.5 -> 378.5 ms with sparse forward 44.3 -> 3.1 ms and sparse backward 28.0 -> 9.1 ms; latency hiding is the largest contributor (removing it costs 12.7% latency vs 1.1-2.9% for the others), training loss curves match. On DLRM/Criteo it is 1.60x over DLRM-Baseline and 1.26x over TorchRec at 8 GPUs (1.84 -> 2.94 M samples/s) by selecting only embedding communication aggregation, with ROC-AUC 0.7883 vs 0.7884.
