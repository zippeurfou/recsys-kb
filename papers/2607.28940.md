## Summary

LinkedIn found that existing recommendation systems using monolithic Transformer models were inefficient because they combined long-term behavior and real-time serving events into one sequence, obscuring their distinct roles. To address this, they introduced TransX, an encoder-decoder architecture reformulating recommendations as predicting next user actions ("action transduction") by explicitly separating behavioral encoding from the serving model. A key innovation is a co-designed amortized serving strategy that uses incremental behavior updates and per-request caching to reduce real-time computation costs significantly (80%) while maintaining performance comparable or better than state-of-the-art models (+6% CTR lift, +4.4% conversion gain).

## Technical note

Monolithic generative recommenders flatten long-term user behavior and system serving events into one token stream, conflating two different generative processes and forcing the whole behavior prefix to be re-encoded per request. TransX (LinkedIn) recasts ranking as sequence-to-sequence action transduction with an asymmetric encoder-decoder: a 2-layer causal Transformer with relative position encoding encodes the behavior stream over a 180-day window; candidates then 'cross' it via grouped multi-query sparse cross-attention, where all m candidates of a serving event share behavior-derived keys/values but keep candidate-specific queries and attend only to the last L_local=10 behavior tokens plus one attention-pooled global anchor; a query-key softmax decoder over learnable action-token embeddings (click / view / dismiss) then decodes all candidates in parallel and non-autoregressively, a choice made explicitly for calibration so all action probabilities share a single normalization. Causality lets the entire behavior stream be encoded once per user and prefix-sliced per event, dropping training cost from O(T*L^2*d) to O(L^2*d + T) (about 50% faster per epoch); at serving, behavior encodings are computed nearline, bf16-quantized and cached per viewer, and request-level KV caching makes the marginal cost of an extra candidate independent of sequence length. Offline on LinkedIn's largest social recommendation dataset TransX reaches 0.862 AUC / 0.273 AUPR / 0.648 gAUC versus 0.860/0.271/0.644 for TransAct-append and 0.858/0.269/0.645 for a Meta-GRM-style monolithic baseline, at 3.8e2 offline but only 0.6e2 online MFLOPs (roughly 20% of the baselines' online compute); ablations rank the encoder stack as most critical (-28.3% AUC), then cross-attention (-13.4%), while replacing sparse with full global cross-attention buys only +4.5% AUC at ~4x the online compute. A 50/50 online A/B against the production DLRM lifts CTR +6.0% and conversion +4.4% (both p<1e-4) plus +0.26% DAU, with the serving co-design cutting p99 latency by up to 83% at 500 candidates per request.

- All models in our offline benchmarking experiments are trained using the Adam optimizer with an initial learning rate of 0.001. We adopt a learning-rate schedule consisting of linear warmup followed by cosine decay. Model selection is performed based on validation AUC with early stopping, and all reported offline metrics are computed on the held-out test set
- All models are implemented with TensorFlow 2.11 library and trained on an on-premise NVIDIA H100 GPU cluster under identical hardware and software configurations to ensure fair comparison
- Across all models, including discriminative baselines, action-transduction models, and next-action generation models, we use the same binary cross-entropy loss for click and no-click prediction. For models that predict action distributions, the binary loss is applied consistently to the click action to align evaluation objectives across architectures
- To control model capacity, we fix the number of Transformer blocks to two for all Transformer-based baselines and TransX. Model width, including projection and FFN hidden dimensions, is adjusted to approximately match MFLOPs across models. After capacity matching, dropout rate is treated as the primary hyperparameter and tuned on the validation set
- Unless otherwise stated, all models are trained with the same batch size, sequence construction and tokenization, user / item / contextual features, and data preprocessing pipelines, ensuring that performance differences are attributable to architectural design rather than training or data artifacts
- Offline training. We train a lightweight backup model on cold-start traffic that excludes the behavior-stream encoder and cross-attention components, relying solely on event-level, user, and candidate features
- Online serving. During inference, the serving backend first attempts to retrieve the cached behavior-stream encoding for the requesting user. If no cache entry is found (e.g., for new or returning users), the system automatically falls back to the backup model and serves recommendations using only event-level features
- Warm start. During initial model launch, for members with eligible behaivor sequence, we pre-compute all user’s behaivor encoding representations and persist them in on-disk cache. For newly active users, behavior representations are incrementally materialized and cached upon the first few serving events with positive engagement
- Lifecycle. Cached representations are stored with a time-to-live (TTL) and evicted based on recency of access, ensuring that memory usage scales with the set of active users rather than total user population
- Versioning and consistency. Cached entries are versioned by both the model identifier and the feature schema version. Upon model upgrades or feature changes, stale cache entries are automatically invalidated, preventing mismatches between cached representations and the active serving model
- Failure recovery. In the event of cache corruption, eviction spikes, or transient storage failures, the serving system will fall back to the cold-start backup model and resume on-the-fly behavior encoding
- for highly active users, we adopt a Kafka-based streaming pipeline that continuously ingests user interaction events. Behavior updates are processed / encoded incrementally, and used to refresh the cached behavior-stream encodings in near real time. This setup enables low-latency incorporation of new user actions while amortizing computation across events
- for other users, we employ an HDFS-based batch pipeline. In this mode, user behavior events are periodically aggregated over fixed time windows and used to recompute behavior-stream encodings in bulk
- amortized encoding significantly reduces latency and achieving near-linear scaling,
- KV caching further stabilizes latency growth,
- the reduction in latency is more pronounced for larger candidate set size
